# Fretlane

(Formerly "Songstarr". The app name lives in `shared/brand.ts`; the GitHub repo is `mauritsE/Fretlane`.)

A local-first, open-source Songsterr-style tab player. The browser app (vanilla TypeScript + Vite + alphaTab) talks to a small Node server that stores the library in `library/` as `songs.json` plus tab files.

## Architecture
- `server/app.ts`: `startServer()`, the shared HTTP server. `server/index.ts` is the npm entry (dev/`npm start`); `desktop/main.ts` is the desktop-app entry (Electron: runs the server in-process, shows the UI in a native window, library in `~/Fretlane`).
- `server/index.ts`: CLI entry for the `node:http` server bound to 127.0.0.1. Serves `/api/songs` (CRUD + `/:id/tab` + `/:id/audio`: raw-body PUT upload, GET with HTTP ranges) and `/api/fetch?url=` (tab download proxy), plus `dist/` when started with `--serve-dist`.
- `server/library.ts`: JSON "database" with atomic writes, format detection, and ASCII→alphaTex conversion on import. Seeds `demo/` on first run. Users' own audio files live in `library/audio/<song id>.<ext>`; `shared/audio.ts` detects the format from the file's bytes and parses Range headers.
- `shared/`: pure, tested logic used by both sides (types, YouTube/Spotify link parsing, format detection, `mediaClock.ts`, `asciiTab.ts`, `sync.ts`).
- `shared/songbook.ts` + `shared/music.ts`: generate multi-track alphaTex from `songbook/songs.ts` (note names and chord symbols; fingering is computed). `npm run build-songbook` writes `demo/*.atex`; `tests/songbook.test.ts` checks bar lengths and that alphaTab plays the written pitches.
- `shared/mediaSearch.ts` + `server/mediaSearch.ts` + `src/mediaPicker.ts`: "🔍 Find" in the song dialog. The server searches YouTube (unofficial youtubei/v1/search endpoint, no key) or Spotify (Web API, client credentials from `library/settings.json` or env), and `rankResults` puts studio recordings above covers/lessons/live. `/api/search?source=&q=` and `/api/settings` (never returns the secret).
- `shared/cloud.ts` + `server/cloud.ts` + `src/cloudView.ts`: "☁ Cloud" in the library opens tabs from Fretlane Cloud (the paid storage on the website, repo `mauritsE/fretlane-sync-magic`, Supabase behind it). Sign-in is a device link: the app opens `<site>/connect?return=<loopback>/api/cloud/callback&state=…`, the site redirects back with a one-time `token_hash`, and the server trades it for its own session (refresh token in `library/cloud.json`, mode 600). The library's top bar shows the signed-in account at the right (`accountChip()`, or "Sign in"); it follows the dialog's sign-in/out and re-checks on window focus. Importing a cloud tab adds a normal local song with `cloudId` set; the site's `sync_offset` becomes a pin on bar 1. The other way, `server/cloudSync.ts` backs up every song written in Fretlane while signed in (debounced after each change; a new file per version because the `tabs` bucket has no update policy; `cloudSyncedAt` marks what is uploaded; `GET /api/cloud/sync/:id` feeds the editor's ☁ status). `FRETLANE_CLOUD_SITE` / `_API` / `_KEY` override the endpoints.
- Tab editor (Fretlane Premium, spec in `docs/premium/tab-editor-spec.md`): `shared/editor/doc.ts` is the song document the editor works on (tracks: guitar, bass, ukulele, mandolin, banjo or drums; `fromScore.ts` tells the string instruments apart by tuning preset and MIDI program, since alphaTex doesn't record it); `commands.ts` holds every edit as a pure function (bars keep themselves full with rests) plus undo history; `tex.ts` / `fromScore.ts` convert to alphaTex and back. `src/editorView.ts` (route `#/write/<id>`) re-parses the alphaTex and calls `renderScore()` with `firstChangedMasterBar` after each edit, draws the caret from `boundsLookup`, and autosaves via `PUT /api/songs/:id/tab` (alphaTex, songs with `written: true` only). Typed notes sound through `src/pluck.ts`, not alphaTab's `playNote()` (see the alphatab skill). Premium = the website's Fretlane Cloud plan: `server/cloud.ts#premium()` reads the user's `subscriptions` row and `my_kofi_membership()` RPC (rules in `shared/premium.ts`, 14-day offline grace in `library/premium.json`). The Mac App Store build passes `premiumIncluded` and skips the check.
- Drum tracks in the editor: `kind: 'drums'`, `tuning` holds the General MIDI numbers of `DRUM_KIT` (doc.ts) and a hit is a note whose `string` is the kit lane, so cursor, chords and bar edits work unchanged. `tex.ts` writes them as `\instrument percussion` / `\staff {score}` / `\clef neutral` with every hit in parentheses (a lone `42.8` would read as fret 42 on string 8); `fromScore.ts` maps `percussionArticulations[...].outputMidiNumber` back to lanes. The editor renders a drum track with `StaveProfile.Score` and names the drum above the beat, with the caret at that drum's staff position (`drumStaffLine`); a click picks the nearest drum (`drumLaneAt`).
- Riff assistant (Premium, sidebar of the editor): `shared/editor/assistant.ts` builds the request: `song` is the whole song (`songText()`: structure, every track, every bar as beat lists, repeated bars and rests shortened, capped at `MAX_SONG_CHARS` around the focus) sent first with `cache_control` so a retry reads it from the prompt cache, and `focus` names the selected bars or where the new part goes, with those (or the two bars before) as ASCII tab, holds the system prompt and the structured-output schema (`parts`: one per track, existing or new, guitar/bass/drums), and fits Claude's answer back in (`riffFromAnswer`, `applyRiff`: improve replaces the selected bars on the tracks it writes, generate fills bars that are empty on those tracks from the cursor and inserts before any bar with notes; new tracks are added at the end). `server/assistant.ts` calls Claude (`claude-opus-5-5`, `@anthropic-ai/sdk`, streamed; logs token usage per request) with `FRETLANE_ANTHROPIC_API_KEY` if set, else `FretlaneCloud#riffAssistant()` posts to the website's `/api/public/app/riff-assistant`, which checks the plan and its monthly assistant bars (one bar on one track; $5 = 96, $25 = 480, $50 = 1152, rules in the site's `src/lib/aiPlans.ts`), calls Claude with the site's key, charges the bars written and returns `usage` (and a `notice` when parts were left out). `GET /api/assistant/status` (`FretlaneCloud#assistantStatus()`, a GET on the same website route) says whether the assistant can be used (`own-key`, `ok`, `signed-out`, `no-plan`, `unknown`) with the month's usage: the editor draws the bar under the assistant from it (`usageMeter()`), and without a paid plan keeps the box visible but locked, with a Sign in or Upgrade button (the Mac App Store build includes the editor, not the assistant). The website has a port of the prompt and schema in `src/lib/riffAssistant.ts`: keep the two in step.
- `src/metronome.ts`: Web Audio metronome panel (timing maths in `shared/metronome.ts`).
- `src/playerView.ts`: alphaTab setup and the recording ↔ alphaTab bridge (external-media mode plus sync points). The recording is a `MediaPlayer` (`src/media.ts`): `src/youtube.ts`, `src/spotify.ts` or `src/audioFile.ts` (an `<audio>` element). A song has at most one of `youtubeId`, `spotifyId` and `audioFile`, because sync pins belong to one recording. For audio files the sync panel shows `src/waveform.ts` (canvas; peaks, onset snapping and the view window are in `shared/waveform.ts`). alphaTab's own stop() at the end of the tab seeks back to bar 1; the bridge ignores that seek while the recording is paused, so scrubbing into an outro sticks. `src/libraryView.ts`: library grid and the add/edit dialog.

## Conventions
- TypeScript everywhere, strict mode, no framework. DOM is built with the `h()` helper in `src/dom.ts`.
- Keep maths and parsing in `shared/` so vitest can cover it. Keep browser-only code in `src/`.
- Do not bundle or fetch copyrighted tabs. Demo tabs must be original; songbook songs must be public-domain melodies (traditional, or composers who died long ago) in our own arrangements.

## Skills (in `.claude/skills/`)
- `fretlane-add-song`: importing songs and setting up sync pins.
- `fretlane-verify`: the verification routine (typecheck, vitest, Playwright e2e with fake YouTube and Spotify, production run) and environment gotchas.
- `fretlane-release`: building, verifying and publishing the desktop app (Electron) for non-technical users.
- `alphatab-integration`: alphaTab facts learned the hard way (Vite asset setup, external media API, sync points, alphaTex, the string-numbering quirk).

## Which model for which task
- **Haiku (Explore agent):** read-only lookups such as grepping `alphaTab.d.ts` for exact signatures or finding where something lives. Fast and cheap, and verbatim extraction is all it needs to do.
- **Sonnet:** well-specified implementation from a clear spec, e.g. writing a test suite for existing pure modules or adding a self-contained importer. Tell it to report source bugs rather than weaken assertions. That is how the `resolveTuning` crash and the sync-pin normalization gap were found.
- **Opus (main session):** architecture and cross-cutting integration (the YouTube/alphaTab clock bridge), debugging in the real browser, reviewing subagent output, and anything user-facing.
